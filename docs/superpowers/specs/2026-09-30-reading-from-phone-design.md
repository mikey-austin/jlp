# 読解 from the phone: bookmarklet and share target — design

**Goal:** make a Kindle study edition from an article read in Chrome on
Android, where the learner is signed in to WSJ and other sites, by
handing it to JLP from the phone instead of from the desktop extension.

**Status:** approved in conversation 2026-09-30.

## The constraint

Neither the JLP PWA nor the JLP server can use the phone browser's WSJ
session: the browser isolates each site's pages and cookies, and a
server fetch meets the paywall (and would break the rule that the server
never fetches an article's page). So, as on desktop, the text must be
read **inside the article's own page**, where the learner is signed in,
and handed to JLP from there. Chrome on Android runs no extensions.

Images are different: the image CDNs checked (images.wsj.net, NHK) send
`Access-Control-Allow-Origin: *`, so a JLP page can fetch image bytes
itself from the URLs the capture found.

## Two paths

### 1. Bookmarklet (main path: full article, images, metadata)

**Setup.** A settings page, 設定 → 「スマホで読解」 (`/settings/phone`),
shows the bookmarklet and how to save and use it in Chrome on Android
(type its name in the address bar, pick the bookmark suggestion). The
bookmarklet is generated by the server from the extension's own
`chrome-extension/article.js`, embedded in the Go binary through a small
package in `chrome-extension/`, so there is one capture implementation
and the phone and desktop can never drift. The capture code is inlined
in the bookmark (line comments stripped) because a news site's content
security policy can block loading a script from JLP.

**Use.** On an article the bookmarklet runs the capture, then opens
`<JLP>/reading/capture` in a new tab. The handoff is `postMessage`,
which a site's CSP does not restrict:

1. The capture page posts `{type: "jlp-capture-ready"}` to
   `window.opener` (target `*`; it carries nothing) every second for
   20 s.
2. The bookmarklet accepts `ready` only from the window it opened
   (`event.source === w`) and from JLP's origin, then posts
   `{type: "jlp-capture-article", v: 1, article}` to that window with
   target origin JLP — no other origin can read it. It stops listening
   after 5 minutes (long enough for a login round trip).
3. The capture page accepts `jlp-capture-article` only from
   `window.opener` and validates its shape.

**Confirm.** Any web page could open `/reading/capture` and message it,
so the page never submits on its own: it shows a card — title, source,
character count, 「画像 n枚」 — and one button, 「作成してKindleに送る」.
A hostile page therefore cannot spend model calls or mail the Kindle.

**Submit.** The page fetches and downscales the images with the
extension's own image code (`chrome-extension/imaging.js`, extracted
from `popup.js` and embedded and served by JLP too: same limits — long
side ≤ 1200 px, ≤ 2 MB each, ≤ 12, ≤ 14 MiB total, 10 s per fetch,
images under 200 px dropped), then POSTs the existing multipart
`/api/v1/reading/articles` from JLP's origin with the session cookie
and `deliver: true`. Any failure of the multipart request other than
401/403 retries once as text-only JSON (server dedupe makes that safe).
Then it navigates to `/reading/{edition}`, which shows progress and the
lesson; the edition is mailed to the Kindle when ready.

### 2. Share target (fallback: text only, zero setup)

**Registration.** The PWA manifest gains a `share_target`:
`action: "/reading/share"`, `method: "POST"`,
`enctype: "application/x-www-form-urlencoded"`, params `title`, `text`,
`url`. With the PWA installed, JLP appears in Android's share sheet.

**Receipt in the service worker.** The worker intercepts
`POST /reading/share`, stores the fields in a dedicated Cache Storage
cache (`jlp-share`, which the worker's activate step must not delete)
under a random id, and answers `303` to `/reading/share?pending=<id>`.
Handling it in the worker avoids depending on whether a share-launched
POST navigation carries the SameSite=Lax session cookie or passes the
CSRF check. If the worker is not installed yet, the server answers the
POST with the share page and a message asking to reopen JLP and share
again.

**Share page.** `/reading/share` reads and deletes the stored entry and
shows a confirm card like the capture page's — title, character count,
the source URL if any, a note that it is text only — and submits only on
the learner's tap of 「作成してKindleに送る」 (text-only JSON with
`deliver: true`, then `/reading/{edition}`). Ruling (final review): the
worker parks *any* POST to `/reading/share`, including a hostile
cross-site one that bypasses the server's CSRF check, so arriving at the
page proves no intent; the tap is what keeps "a hostile page cannot
spend model calls or mail the Kindle" true.

- A trailing line that is only a URL becomes the source URL; the title
  is the shared `title`, else the first line (clipped to 80 runes).
- If what remains is empty (the learner shared only the page link), the
  page says 「URLだけでは本文を読めません。本文を選択して共有するか、
  ブックマークレットを使ってください」 and submits nothing.

## Server changes

- The bookmarklet's origin is derived from the request alone (scheme
  from the first `X-Forwarded-Proto` value if `http`/`https`, else TLS,
  and `Host`). There is no `PublicURL` option: `server.baseurl` has a
  dev default that is wrong for every other deployment.
- `GET /settings/phone`, `GET /reading/capture`, `GET` and
  `POST /reading/share` — all behind the normal session login.
- `GET /static/ext/{article.js|imaging.js}` serving the embedded
  extension files with a content-hash query and long cache lifetime.
- The manifest's `share_target`; the service worker's share handler.
- JLP sets no CSP or COOP today (nor does the Caddy vhost). Adding a
  COOP later would sever the bookmarklet's `window.opener`, and a CSP
  would have to allow image CDNs in `connect-src`; the spec records that
  so a future header change does not silently break this.

## Failure handling

| Situation | Result |
|---|---|
| Capture page opened directly, or no article within 20 s | 「記事が届きませんでした。記事のタブでもう一度ブックマークレットを実行してください」 |
| Session expired | normal login round trip; the handoff completes afterwards (opener survives navigation, bookmarklet listens 5 min) |
| Popup blocked (window.open returns null) | the bookmarklet navigates the current tab to `/reading/capture#blocked`, which explains how to allow pop-ups |
| Article too long / not Japanese / empty | the server's existing message on the card; nothing submitted |
| Image fetch/downscale fails | skipped and counted 「画像 n/m枚」 |
| Multipart upload fails (not 401/403) | one text-only retry with a note |
| Share of a URL only | the message above; nothing submitted |
| Worker missing on share | server share page asks to reopen JLP and share again |

## Testing

- **Go:** bookmarklet generation (starts `javascript:`, contains the
  capture code and the JLP origin, line comments stripped, escaped,
  bounded length); `share_target` in the manifest; the new routes
  require login and render; the service worker template carries the
  share handler and keeps the `jlp-share` cache on activate;
  `/static/ext/*` serves the embedded files with cache headers.
- **Browser (desktop Chrome):** run the generated bookmarklet on an NHK
  article and on the learner's logged-in WSJ article; the handoff
  arrives, the card shows, submit creates the edition with images and
  Mailpit (dev) receives it. Post the share form from a JLP page so the
  worker intercepts it; check auto-submit and the URL-only message.
  Re-verify the extension popup after the `imaging.js` extraction.
- **On the phone after deploy:** the Android share sheet and the
  bookmarklet in Chrome for Android.

## Out of scope

The MHTML "save page and share the file" route; iOS/Safari; images on
the share-text path; a per-learner auto-send setting (the phone always
auto-sends).
